# AGENTS.md

## Source of Truth

### API contract

`01-analysis/api/openapi.yaml` — единственный канонический контракт Client API.

- Запрещено менять пути, типы параметров, DTO, обязательность полей и коды ответов `200`, `201`, `400`, `409` без согласованного изменения контракта.
- Изменение OpenAPI сначала отражается в требованиях и затем генерирует/обновляет клиентские DTO и API-интерфейсы.
- Клиент не добавляет собственные поля, эндпоинты или альтернативные коды ошибок.
- Источник истины по местам, броням и статусам — существующий backend, а не локальное состояние приложения.

### Product rules

`01-analysis/2-requirements/` и `01-analysis/5-mobile-app-spec/` — строгие бизнес-правила и экранные контракты.

- `BR-004`: для новичковых тренировок вместимость до 8 человек, для остальных форматов — до 16.
- `BR-005`: одна бронь = один человек; групповое количество в клиенте отсутствует.
- `BR-006`: скальники и страховочная система (обвязка) выбираются раздельно; для каждого компонента поддерживаются `own` или `rental`.
- `BR-007`: клиентская отмена разрешена не позднее чем за 2 часа до старта по серверному времени.
- `BR-011`: в MVP нет онлайн-оплаты; используется только `payment_method = on_site`.
- `BR-013`: при конкуренции за место backend возвращает отказ, приложение не создаёт подтверждённую или фантомную бронь.
- Изменение этих правил требует обновления BR, затронутых FR, screen spec, API-контракта и `PROMPTS_LOG.md`.

### Change control

- Перед реализацией прочитать `AGENTS.md`, релевантные BR/FR/NFR, `SCR`-спецификацию и OpenAPI.
- Не молча исправлять противоречие между документами: зафиксировать решение или остановить задачу для уточнения.
- Новые поля и статусы без traceability ID не принимаются.

## Code Architecture & Modularization

### Stack and modules

- Клиент: Compose Multiplatform на Kotlin.
- Модули клиента: `client`, `androidApp`, `desktopApp` и отдельный `local-backend` для разработки.
- Общие UI, domain и data-классы размещаются в `client/src/commonMain`.
- Платформенные файлы остаются в platform source sets и не дублируют бизнес-логику.

### Package-by-feature

Строгий путь для feature-кода:

```text
client/src/commonMain/kotlin/org/example/client/features/<feature_name>/...
```

Название feature соответствует доменному сценарию, например `auth`, `schedule`, `booking`. Запрещены общие плоские пакеты вроде `components/`, `models/`, `screens/` для всей фичи.

### Feature layers

Внутри каждой фичи используются три слоя:

- `presentation/`: Compose UI, отдельные Composable-файлы, ViewModel, UI State и navigation events.
- `domain/`: доменные модели, правила и UseCases без зависимости от Ktor или Compose.
- `data/`: Ktor API, DTO, мапперы, cache и repository implementations.

Зависимости направлены внутрь: `presentation → domain ← data`. Domain-слой не знает о DTO, HTTP, Android и Compose.

### Жесткое ограничение монолита

- Запрещено создавать файлы длиннее 150–200 строк; предпочтительная цель — до 150 строк.
- Каждый Composable-экран оформляется отдельным файлом.
- Каждый DTO, UI State, ViewModel, UseCase, mapper и repository обязан находиться в отдельном файле; объединять можно только небольшие связанные тестовые fixtures или ресурсы, но не смешивать слои.
- `App.kt` содержит только bootstrap, DI-границы, навигационный shell и вызовы корневого приложения; feature-логика, DTO и бизнес-правила в нём запрещены.
- Запрещено дублировать один и тот же DTO вручную в нескольких feature-модулях: используется общий контрактный слой или генерация из OpenAPI.
- Новый файл должен иметь одну понятную ответственность и не скрывать соседние слои.

## Networking & Local Infrastructure

### Ktor Client

- Базовый клиент: Ktor Client с плагином `Logging` на уровне `HEADERS/BODY` в System log/console.
- `ContentNegotiation` использует JSON и `ignoreUnknownKeys = true`.
- Logging включается только в debug/dev профиле. В production заголовок `Authorization`, OTP, телефон и push token редактируются или отключаются; body не должен содержать секреты.
- Base URL передаётся через конфигурацию окружения, а не зашивается в feature-код.

### Base URL

- Android Emulator: `http://10.0.2.2:8080`.
- Desktop и локальный запуск: `http://127.0.0.1:8080`.
- Значение должно переопределяться конфигурацией или аргументом запуска без изменения feature-кода.
- Production URL не подставляется вместо локального значения без изменения окружения и проверки контракта.

### Android network security

В `androidApp` обязательно наличие `network_security_config.xml` с разрешением Cleartext HTTP только для:

- `10.0.2.2`;
- `127.0.0.1`;
- `localhost`.

Глобальный cleartext для произвольных доменов запрещён. В production используется HTTPS.

### Local backend

- Локальный backend — Go/PostgreSQL в Docker только для разработки и тестов.
- Он реализует или мокает операции `01-analysis/api/openapi.yaml`; production-инфраструктура остаётся внешней black-box системой.
- Docker Compose не содержит секреты в открытом виде; credentials поступают из env или локального `.env`, который не коммитится.
- Миграции PostgreSQL, healthcheck и deterministic fixtures проверяются до начала feature-разработки.

## UI, State and Data Rules

- Каждый экран из `01-analysis/5-mobile-app-spec/` реализуется с состояниями Initial, Loading, Success, Empty, Error, Offline и Forbidden.
- Network state не смешивается с Empty State: отсутствие сети не означает отсутствие тренировок.
- Расписание кэшируется read-only; кэш получает метку неактуальности.
- Создание брони, отмена и оценка блокируются Offline; локальный `confirmed` не создаётся без ответа API.
- `409 Conflict` обрабатывается как конкуренция: обновляется источник истины, но не создаётся фантомная бронь.
- Повторные нажатия блокируются на время активной операции.
- Даты и дедлайны сравниваются с серверным временем, а не только с часами устройства.
- UI-тексты, доступность, touch target 48 dp и mobile-first ширина 360 dp следуют дизайн-брифу.

## Testing & Quality Rules

- Domain UseCases и мапперы покрываются unit-тестами.
- API слой покрывается contract-тестами по OpenAPI и проверкой схем ответов.
- Обязательные сценарии тестирования: 6-значный OTP, 400/401, 7-дневный дефолт, пустой расписок, Offline, 0 мест и `409 Conflict`.
- Для бронирования выполняется race-тест двух параллельных запросов на последнее место.
- UI-тесты проверяют Loading, Empty, Error, Offline, Forbidden и блокировку повторного submit.
- Перед завершением задачи запускаются доступные lint, typecheck и test-команды проекта.
- Новый код не считается готовым без ссылки на BR/FR/NFR и затронутые `SCR`.

## Git & Workflow Rules

- Используются атомарные коммиты в стиле Conventional Commits: `feat:`, `fix:`, `chore:`, `refactor:`.
- Один коммит содержит одну завершённую логическую единицу работы; анализ, реализация и рефакторинг не смешиваются без необходимости.
- Перед генерацией кода агент формулирует план шага: что меняется, какие файлы затронуты, как проверяется и какие требования покрываются.
- Запрещено применять изменения вслепую. Перед записью файлов и перед commit агент проверяет текущие файлы, `git status`, diff и последние коммиты.
- В staged diff попадают только намеренные файлы задачи; чужие изменения не перезаписываются.
- Коммит создаётся только при явном запросе пользователя.
- Секреты, токены, пароли, private keys и реальные персональные данные не записываются в репозиторий или логи.
- После завершения сессии обновляется `PROMPTS_LOG.md` с запросом, решениями, артефактами и проверками.

## Agent Definition of Done

1. План шага сформулирован до генерации.
2. Изменения соответствуют OpenAPI, BR/FR/NFR и `SCR`-спецификациям.
3. Новые файлы находятся в правильных feature/package слоях и не создают монолит.
4. Добавлены или обновлены тесты для затронутого поведения.
5. Выполнены доступные lint, typecheck и test-команды.
6. Проверены diff и рабочее дерево.
7. Пользователь получил краткий отчёт и следующий шаг.
