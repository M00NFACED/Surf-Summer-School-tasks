# 01 — Бизнес-требования MVP

## 1. Метаданные

| Поле | Значение |
|---|---|
| Документ | `BR-MVP-001` |
| Назначение | Каноническая декомпозиция бизнес-требований к MVP |
| Заказчик | Скалодром «Вертикаль» |
| Роль | Клиент |
| Статус | MVP baseline |
| Источники | `01-analysis/0-customer-brief/customer-brief.md`, `01-analysis/1-elicitation/customer-questions.md`, `01-analysis/1-elicitation/domain-description.md` |
| Скоуп | Мобильное приложение Клиента и Client API |
| Приоритизация | MoSCoW |

## 2. Бизнес-цели

| ID | Бизнес-цель | Результат для скалодрома | Результат для клиента |
|---|---|---|---|
| BG-001 | Снизить ручную обработку записей | Владелец не проверяет каждую запись вручную | Клиент записывается самостоятельно |
| BG-002 | Исключить переполнение и двойные брони | Слоты используются в пределах установленной вместимости | Клиент получает подтверждение только при реальном свободном месте |
| BG-003 | Сделать изменения прозрачными | Клиенты видят актуальный статус тренировки и причину отмены | Клиент понимает, что произошло с записью |
| BG-004 | Снизить неявки | Через правило окна отмены и напоминания часть мест освобождается вовремя | Клиент может управлять своей записью |
| BG-005 | Запустить полезный MVP в ограниченном бюджете | В работу входят только критичные клиентские функции | Клиент получает базовый сервис без лишних интеграций |

## 3. Правила MoSCoW

| Категория | Требования |
|---|---|
| Must | BR-001, BR-002, BR-003, BR-004, BR-005, BR-006, BR-007, BR-008, BR-012, BR-013, BR-014 |
| Should | BR-009; необязательные напоминания из BR-010 |
| Must с уточнением | BR-010: push при отмене скалодромом обязателен, напоминание о тренировке остаётся Should |
| Won't | BR-011: онлайн-оплата, платёжный шлюз, чеки, возвраты и онлайн-транзакции |

Метрики ниже являются измеримыми целями пилота MVP. Внутренняя SLA, транзакционность и реализация существующего бэкенда не входят в эту оценку.

## 4. Каталог бизнес-требований

### BR-001 — Самостоятельная запись клиента

- **Формулировка:** Клиент может найти свободный слот и самостоятельно оформить запись через мобильное приложение.
- **MoSCoW:** Must.
- **Бизнес-цель:** BG-001.
- **Метрика успеха:** к концу пилотного месяца не менее 90% успешно подтверждённых записей оформлены клиентом в приложении без ручного подтверждения владельцем.
- **Источник:** `customer-brief.md`, строки 15–17; `domain-description.md`, BR-001.
- **Связи:** US-001, US-002, UC-001, UC-002, FR-001, FR-002.

### BR-002 — Информация о слоте

- **Формулировка:** Карточка слота предоставляет клиенту время, формат или зону, инструктора, количество свободных мест и адрес зала.
- **MoSCoW:** Must.
- **Бизнес-цель:** BG-001, BG-003.
- **Метрика успеха:** 100% отображаемых слотов содержат все обязательные поля из контракта; 0 карточек с обязательным пустым полем.
- **Источник:** `customer-brief.md`, строки 21–24; уточнение R-015; `domain-description.md`, BR-002 и BR-014.
- **Связи:** US-002, US-003, UC-002, FR-002, FR-003.

### BR-003 — Горизонт расписания

- **Формулировка:** При первом открытии расписания показываются слоты на ближайшие 7 дней от текущего момента; клиент может изменить период фильтрацией по дате.
- **MoSCoW:** Must.
- **Бизнес-цель:** BG-001, BG-003.
- **Метрика успеха:** не менее 95% открытий расписания используют 7-дневный диапазон по умолчанию; при отсутствии слотов на этом диапазоне 100% случаев показывают Empty State.
- **Источник:** уточнение R-027; `customer-questions.md`, BR-003; `domain-description.md`, BR-003.
- **Связи:** US-002, UC-002, FR-002, NFR-001, NFR-007.

### BR-004 — Вместимость групп

- **Формулировка:** Новичковые тренировки вмещают до 8 человек, остальные форматы — до 16 человек; подтверждение места выполняет существующий бэкенд.
- **MoSCoW:** Must.
- **Бизнес-цель:** BG-002.
- **Метрика успеха:** 0 подтверждённых броней сверх лимита в приёмочном наборе; 100% ответов о нехватке мест обрабатываются как отказ без фантомной брони.
- **Источник:** `customer-brief.md`, строка 23; `customer-questions.md`, Q-002; `domain-description.md`, BR-004.
- **Связи:** US-004, UC-003, FR-004, NFR-002, NFR-003.

### BR-005 — Бронь на одного человека

- **Формулировка:** Одна бронь относится к одному клиенту; для нескольких участников создаются отдельные брони.
- **MoSCoW:** Must.
- **Бизнес-цель:** BG-002.
- **Метрика успеха:** 100% созданных записей содержат одного владельца-клиента; в интерфейсе отсутствует групповое количество участников.
- **Источник:** `customer-questions.md`, Q-002, выбранный дефолт; `domain-description.md`, BR-005.
- **Связи:** US-004, US-005, UC-003, FR-004, FR-007.

### BR-006 — Выбор снаряжения и проката

- **Формулировка:** При бронировании клиент выбирает своё снаряжение, прокат скальников и/или прокат страховочной системы; наличие и тариф предоставляет Client API.
- **MoSCoW:** Must.
- **Бизнес-цель:** BG-001, BG-005.
- **Метрика успеха:** 100% подтверждённых записей содержат явный выбор по каждому требуемому компоненту; 100% запросов проката показывают тариф и наличие на момент ответа API.
- **Источник:** `customer-brief.md`, строка 24; `customer-questions.md`, Q-003; уточнение R-015.
- **Связи:** US-004, UC-003, FR-005, FR-006, NFR-003.

### BR-007 — Окно клиентской отмены

- **Формулировка:** Клиент может отменить бронь не позднее чем за 2 часа до времени начала тренировки по времени источника истины.
- **MoSCoW:** Must.
- **Бизнес-цель:** BG-003, BG-004.
- **Метрика успеха:** 100% запросов отмены проверяются серверным временем и дедлайном; 0 успешных клиентских отмен при остатке менее 2 часов.
- **Источник:** `customer-questions.md`, Q-001, выбранный дефолт; `domain-description.md`, BR-007.
- **Связи:** US-006, UC-004, FR-008, NFR-003.

### BR-008 — Отмена тренировки скалодромом

- **Формулировка:** При отмене организатором тренировка получает статус «Отменена скалодромом», клиент видит причину, получает push-уведомление и не может повторно записаться в отменённый слот.
- **MoSCoW:** Must.
- **Бизнес-цель:** BG-003.
- **Метрика успеха:** 100% затронутых активных записей отображают статус и причину; 100% событий инициируют push-запрос; 0 запросов повторной записи в отменённый слот принимаются.
- **Источник:** уточнение R-008; `customer-questions.md`, Q-004; `domain-description.md`, BR-008.
- **Связи:** US-007, UC-005, FR-009, FR-011, NFR-003.

### BR-009 — Оценка инструктора

- **Формулировка:** После завершения тренировки клиент может один раз оставить инструктору оценку от 1 до 5 звёзд.
- **MoSCoW:** Should.
- **Бизнес-цель:** BG-003, BG-005.
- **Метрика успеха:** действие оценки доступно для 100% завершённых записей; не менее 20% завершённых записей получают оценку в течение 7 дней после пилота.
- **Источник:** `customer-brief.md`, строка 26; `customer-questions.md`, Q-005; `domain-description.md`, BR-009.
- **Связи:** US-008, UC-006, FR-010, NFR-006.

### BR-010 — Push-уведомления

- **Формулировка:** Клиент может получать push-уведомление об отмене тренировки; напоминание о записи отправляется только при отдельном разрешении.
- **MoSCoW:** Must для отмены скалодромом; Should для напоминаний.
- **Бизнес-цель:** BG-003, BG-004.
- **Метрика успеха:** 100% событий отмены скалодромом инициируют push-запрос; в пилотном измерении не менее 95% push-сообщений доставляются в течение 5 минут при доступном внешнем сервисе.
- **Источник:** `customer-brief.md`, строки 30 и 32; `customer-questions.md`, Q-006; `domain-description.md`, BR-010.
- **Связи:** US-007, UC-005, FR-011, NFR-005.

### BR-011 — Оплата на месте

- **Формулировка:** В MVP приложение фиксирует намерение оплатить на месте, но не принимает онлайн-платежи и не создаёт платёжные транзакции.
- **MoSCoW:** Won't для онлайн-оплаты; обязательное отображение способа оплаты для брони.
- **Бизнес-цель:** BG-005.
- **Метрика успеха:** 0 онлайн-платёжных транзакций; 100% подтверждений брони содержат явное указание «Оплата на месте».
- **Источник:** решение скоупа; `customer-questions.md`, Q-003; `domain-description.md`, BR-011.
- **Связи:** US-004, UC-003, FR-006, NFR-002.

### BR-012 — Ограниченная роль и поставка

- **Формулировка:** Поставка включает только мобильное приложение Клиента и Client API, интегрированные с готовой внешней инфраструктурой.
- **MoSCoW:** Must.
- **Бизнес-цель:** BG-005.
- **Метрика успеха:** 0 пользовательских экранов и API-команд для ролей Администратор или Инструктор; 100% клиентских сценариев используют Client API.
- **Источник:** уточнение R-028; `domain-description.md`, BR-012 и разделы 3, 8.
- **Связи:** US-001, US-002, US-003, US-004, US-005, US-006, US-007, US-008; UC-001–UC-006; FR-001–FR-011.

### BR-013 — Источник истины и защита от конкуренции

- **Формулировка:** Существующий бэкенд атомарно проверяет место и является источником истины; клиент безопасно обрабатывает конкурентный отказ.
- **MoSCoW:** Must.
- **Бизнес-цель:** BG-002, BG-003.
- **Метрика успеха:** 0 двойных и фантомных броней в сценарии race condition; 100% ответов HTTP 409 не переводят локальную форму в подтверждённую бронь.
- **Источник:** уточнение R-004; `domain-description.md`, BR-013.
- **Связи:** US-004, US-006, US-007; UC-003, UC-004, UC-005; FR-004, FR-008, FR-009; NFR-002, NFR-003.

### BR-014 — Доступность данных через Client API

- **Формулировка:** Client API предоставляет данные слота, формата, зоны, инструктора, адреса, проката и статуса, необходимые клиентскому приложению.
- **MoSCoW:** Must.
- **Бизнес-цель:** BG-001, BG-003.
- **Метрика успеха:** 100% обязательных полей контракта присутствуют и проходят проверку схемы для каждого поддерживаемого сценария.
- **Источник:** уточнение R-015; `domain-description.md`, BR-014 и раздел 9.
- **Связи:** US-002, US-003, US-004; UC-002, UC-003; FR-002, FR-003, FR-005; NFR-001, NFR-006.

## 5. Зависимости бизнес-требований

| Зависимость | Требования | Следствие |
|---|---|---|
| Существующий бэкенд атомарно проверяет место | BR-004, BR-013 | Клиент показывает предварительный остаток, но доверяет только подтверждению API |
| Client API возвращает полный контракт | BR-002, BR-006, BR-014 | Приложение не создаёт собственные слоты и не восстанавливает легаси-данные |
| Внешний SMS-сервис | BR-001, BR-012 | Вход возможен только после проверки кода |
| Push-сервис | BR-008, BR-010 | При недоступности уведомления статус всё равно синхронизируется при открытии приложения |
| Оплата на месте | BR-011 | В API отсутствует платёжный шаг MVP |

## 6. Контроль границ MoSCoW

Функция, не поддерживающая хотя бы одну строку каталога BR-001…BR-014, не принимается в MVP без отдельного изменения требований. Онлайн-оплата и административные/инструкторские функции фиксируются как Won't, а не как отложенные обязательные элементы.
