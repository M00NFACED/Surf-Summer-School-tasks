| ID | Категория | Измеримое требование | Порог / критерий |
|---|---|---|---|
| NFR-001 | Производительность | Открытие расписания | Не более 2 секунд |
| NFR-002 | Производительность | Отклик API бронирования | Не более 1,5 секунды |

## 3. Условия измерения

- Для NFR-001 и NFR-002 измерение выполняется на поддерживаемом устройстве при стабильном соединении; в отчёт попадают не менее 20 последовательных запусков, целевой показатель — 95-й перцентиль.
- Время NFR-001 измеряется от перехода на экран расписания до появления первого полезного списка или кэшированного состояния с пометкой.
- Время NFR-002 измеряется от отправки запроса бронирования до получения терминального ответа Client API.
- Тестирование HTTP 409 выполняется с двумя параллельными запросами на последнее свободное место.
- Кэш считается валидным для проверки только при наличии ранее сохранённого расписания.

## 4. Детализированные требования

### NFR-001 — Производительность открытия расписания

Клиентский экран расписания должен переходить из состояния загрузки в состояние с полезным списком слотов, состоянием пустого результата или явно помеченным кэшем не более чем за **2 секунды** после открытия экрана при стабильном соединении. Целевой показатель — не более 2 секунд на 95-м перцентиле 20 измерений.

**Проверка:** NFR-001 проходит, если 19 из 20 запусков укладываются в 2 секунды и пользователь не получает неопознанное промежуточное состояние.

**Связи:** BR-003, FR-002, US-002, UC-002.

### NFR-002 — Производительность API бронирования

Client API должен возвращать терминальный ответ на запрос создания брони не позднее чем через **1,5 секунды** после отправки при нормальной нагрузке и стабильном соединении. Целевой показатель — не более 1,5 секунды на 95-м перцентиле 20 запросов.

**Проверка:** NFR-002 проходит, если не менее 19 из 20 запросов завершаются успешным ответом или корректным конфликтом за отведённое время; клиент не создаёт локальное подтверждение до ответа.

**Связи:** BR-004, BR-013, FR-004, FR-006, US-004, UC-003.

### NFR-003 — Конкурентность и отсутствие фантомных броней

При получении **HTTP 409 Conflict** приложение обязано в **100% случаев**:

- не создавать локальную подтверждённую бронь;
- не показывать запись в разделе «Мои записи» как подтверждённую до повторной сверки с API;
- показать сообщение о недоступности места;
- обновить остаток мест или статус слота при следующем запросе.

Приёмочный сценарий с двумя параллельными запросами на одно место не должен приводить к двум подтверждённым броням.

**Связи:** BR-004, BR-005, BR-007, BR-008, BR-013; FR-004, FR-008, FR-009; US-004, US-006, US-007; UC-003, UC-004, UC-005.

### NFR-004 — Формат телефона

Поле телефона принимает и передаёт в Client API только строки, соответствующие формату E.164 для указанного рынка: `+7XXXXXXXXXX`, то есть знак `+`, код `7` и ровно 10 цифр. В **100% невалидных вводов** запрос кода SMS не отправляется; в **100% валидных вводов** запрос проходит форматную проверку.

**Проверка:** набор допустимых примеров принимается, а пробелы, буквы, короткие номера и неверный код страны отклоняются с понятным сообщением.

**Связи:** BR-001, BR-012; FR-001; US-001; UC-001.

### NFR-005 — Офлайн и кэш расписания

При наличии ранее загруженного расписания приложение должно открыть кэшированный список при отсутствии сети в **100% случаев** и маркировать его как неактуальный. При отсутствии сети приложение должно блокировать **100% попыток создания брони** до восстановления соединения; локальная «Pending» бронь не создаётся.

**Проверка:** при airplane mode пользователь может просмотреть дату, время, формат, инструктора и ранее сохранённую доступность с меткой неактуальности, но не может подтвердить бронь.

**Связи:** BR-003, BR-008, BR-010; FR-002, FR-009, FR-011; US-002, US-005, US-007; UC-002, UC-005.

### NFR-006 — Поддержка экранов от 360 dp

Все клиентские экраны и основные действия должны быть доступны без горизонтальной прокрутки и обрезания полей на ширине **360 dp**. На этой ширине **100%** следующих элементов остаются доступными: время и формат слота, инструктор, свободные места, адрес, кнопка бронирования, фильтры, отмена и выбор оценки.

**Проверка:** тестирование выполняется на ширине 360 dp; каждое действие достигается без обрезания и без необходимости горизонтального скролла.

**Связи:** BR-002, BR-009, BR-012; FR-003, FR-007, FR-010; US-003, US-005, US-008; UC-002, UC-006.

### NFR-007 — Empty State расписания

Если API возвращает **0 доступных тренировок на ближайшие 7 дней**, приложение в **100% случаев** показывает Empty State с сообщением **«Пока нет доступных тренировок»** и возможностью изменить фильтр даты или повторить загрузку. Кнопка успешного бронирования в этом состоянии не показывается.

**Проверка:** сценарий с пустым ответом API и сценарий с фильтром, возвращающим 0 результатов, дают одинаковое понятное состояние без ложных записей.

**Связи:** BR-003; FR-002; US-002; UC-002; NFR-001.
