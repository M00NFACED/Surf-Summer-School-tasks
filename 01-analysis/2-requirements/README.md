# Требования к MVP скалодрома «Вертикаль»

## 1. Назначение каталога

Каталог фиксирует каноническую декомпозицию требований к первому мобильному MVP: от бизнес-цели до функционального поведения, use case, ограничения качества и трассируемости. Источником остаётся клиентский бриф; спорные решения имеют явный дефолт в `../1-elicitation/customer-questions.md`.

## 2. Состав документов

| Файл | Назначение |
|---|---|
| `01-business-requirements.md` | Бизнес-требования BR-001…BR-014, MoSCoW, цели и метрики |
| `02-functional-requirements.md` | Функциональные требования FR-001…FR-011 для приложения и Client API |
| `03-non-functional-requirements.md` | Измеримые NFR-001…NFR-007 |
| `04-user-stories.md` | Пользовательские истории US-001…US-008 с INVEST и критериями приёмки |
| `05-use-cases.md` | Основные сценарии UC-001…UC-006 |
| `06-constraints-and-scope.md` | Границы, ограничения, допущения и зависимости |

## 3. Правила идентификаторов

- `BR-xxx` — бизнес-требование или бизнес-правило.
- `FR-xxx` — проверяемое функциональное поведение.
- `NFR-xxx` — измеримое требование качества.
- `US-xxx` — пользовательская ценность.
- `UC-xxx` — пользовательский сценарий.
- `SCR-xxx` — экран, который будет детализирован в `01-analysis/5-mobile-app-spec/`.

Изменение ID требует обновить все связанные документы и добавить запись в `PROMPTS_LOG.md`.

## 5. Проверка полноты MVP

- Каждый `FR-001…FR-011` имеет минимум одну связь с BR, UC и проверяемым NFR либо явно объясняет отсутствие отдельного измеримого ограничения.
- Каждый `UC-001…UC-006` содержит предусловия, Happy Path, альтернативные потоки и потоки исключений.
- В каждом use case явно обработаны ошибка SMS, конкурентная нехватка мест и отмена после дедлайна либо отмечена неприменимость.
- Онлайн-оплата, админка владельца, интерфейс инструктора и внутренняя БД не имеют FR в MVP.
- Все значения времени и лимитов сначала сверяются с Server-provided данными Client API.
