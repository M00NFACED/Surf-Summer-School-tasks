## 2. Контекст системы

Клиент использует мобильное приложение, которое обращается к Client API. Client API является границей текущей поставки и получает данные о слотах, зонах, инструкторах, прокате и бронях из существующего бэкенда. Существующий бэкенд — источник истины по наличию мест и состоянию брони; его внутренняя реализация не анализируется и не изменяется.

```text
Клиент → Мобильное приложение → Client API → Существующий бэкенд
                                      ↓
                                Push-сервис
Клиент → Оплата на месте

Интерфейс инструктора → Существующая инфраструктура
Админка владельца → Существующая инфраструктура
```

## 3. Роли и зоны ответственности

| Роль или система | Отношение к продукту | Ответственность в MVP |
|---|---|---|
| Клиент | В скоупе | Выбирает тренировку, создаёт и отменяет бронь, выбирает снаряжение, получает уведомления, оставляет оценку |
| Client API | В скоупе | Предоставляет клиенту данные и принимает клиентские команды через согласованный контракт |
| Существующий бэкенд | Внешняя система, black-box | Является источником истины по слотам, местам, броням и конкурентным проверкам |
| Инструктор | Вне скоупа интерфейсов | Ведёт тренировку; его приложение и рабочие процессы уже существуют |
| Администратор / владелец | Вне скоупа интерфейсов | Создаёт и корректирует расписание, управляет ресурсами во внешней системе |
| Push-сервис | Внешняя интеграция | Доставляет уведомление о значимом изменении, прежде всего об отмене скалодромом |
| Касса / оплата на месте | Внешний процесс | Принимает оплату вне мобильного приложения; онлайн-платёж в MVP не создаётся |

## 4. Глоссарий

| Термин | Определение |
|---|---|
| Тренировка | Событие с определённым временем, форматом, зоной и инструктором |
| Слот | Конкретная доступная для записи тренировка в расписании |
| Новичок | Участник формата с инструктажем и повышенными требованиями к технике безопасности |
| Опытный участник | Участник более сложного формата с трассами на верёвке |
| Инструктор | Специалист, который ведёт тренировку; приложение только показывает его данные |
| Бронь | Подтверждённая запись одного клиента на один слот |
| Группа | Набор участников одной тренировки, ограниченный вместимостью слота |
| Вместимость | Максимальное число участников, разрешённое для конкретного слота |
| Свободные места | Количество участников, которое API сообщает как доступное на момент запроса |
| Своё снаряжение | Скальники и/или страховочная система, которые клиент использует сам |
| Прокат | Скальники и/или страховочная система, выдаваемые скалодромом при наличии |
| Отмена клиентом | Отмена брони самим клиентом до наступления дедлайна |
| Отмена скалодромом | Отмена тренировки организатором, например из-за профилактики или проверки снаряжения |
| Оценка инструктора | Оценка от 1 до 5, оставленная клиентом после завершённой тренировки |
| Источник истины | Авторитетный источник статуса; в текущей архитектуре им является существующий бэкенд |

## 6. Нестыковки исходного брифа

| Нестыковка | Решение для MVP | Связанные документы |
|---|---|---|
| Лимит 8 для новичков соседствует с общим лимитом 16 | Разделить лимиты по формату: 8 для новичков, 16 для остальных; фактическое место подтверждает API | BR-004, Q-002 |
| Упомянут запрет отмены за 10 минут, но не указано полное окно | Установить окно 2 часа и не обещать отмену после дедлайна | BR-007, Q-001 |
| «Свои скальники/система» смешивает комплектность и источник снаряжения | Разделить выбор на своё снаряжение и прокат каждого компонента; наличие проверяет API | BR-006, Q-003 |
| Профилактика меняет слот, но не задаёт судьбу брони | Сохранить бронь в статусе «Отменена скалодромом», показать причину и запретить повторную запись | BR-008, Q-004 |
| Письмо просит уведомления, но не определяет их обязательность | Сделать push обязательным для отмены скалодромом, напоминания — по согласию | BR-010, Q-006 |
| Онлайн-оплата упомянута как пожелание | Закрепить Won't: оплата только на месте | BR-011 |

## 7. Жизненный цикл брони

### 7.1. Состояния

| Состояние | Кто переводит | Что означает | Доступные действия клиента |
|---|---|---|---|
| `Доступен` | Существующий бэкенд | Слот доступен для новой брони | Открыть детали, начать бронирование |
| `Оформляется` | Клиентское приложение, временно | Заполняются данные и выбор снаряжения | Заполнить форму, отменить ввод |
| `Подтверждена` | Существующий бэкенд через Client API | Бронь заняла место для одного клиента | Посмотреть детали, отменить до дедлайна, оценить после завершения |
| `Отменена клиентом` | Существующий бэкенд через Client API | Клиент отменил бронь до дедлайна | Повторно забронировать другой доступный слот при наличии |
| `Отменена скалодромом` | Существующий бэкенд | Организатор отменил тренировку; причина обязательна | Посмотреть причину; повторная запись в тот же слот запрещена |
| `Завершена` | Существующий бэкенд | Тренировка состоялась | Оставить оценку, если ещё не оставлена |
| `Оценена` | Существующий бэкенд через Client API | Клиент сохранил оценку инструктора | Просмотреть детали |

### 7.2. Переходы

1. `Доступен` → `Оформляется`: клиент открывает форму.
2. `Оформляется` → `Подтверждена`: Client API подтверждает бронирование и место.
3. `Оформляется` → `Доступен`: клиент отменяет ввод или получает отказ из-за отсутствия места; приложение не создаёт ложную бронь.
4. `Подтверждена` → `Отменена клиентом`: клиент отменяет бронь не позднее дедлайна BR-007.
5. `Подтверждена` → `Отменена скалодромом`: существующая инфраструктура сообщает отмену с причиной.
6. `Подтверждена` → `Завершена`: существующий бэкенд закрывает тренировку.
7. `Завершена` → `Оценена`: клиент сохраняет оценку.

### 7.3. Конкурентные действия

- Показ свободного места не гарантирует возможность бронирования после параллельного действия.
- Перед подтверждением клиентское приложение получает результат атомарной проверки от существующего бэкенда.
- При конфликте места приложение сохраняет заполненные данные формы, показывает понятный отказ и не считает бронь созданной.
- Повторное нажатие «Записаться» во время активного запроса блокируется до получения ответа.
- Статус слота и бронь повторно сверяются при открытии деталей и после push-события.

## 8. Системные границы

### 8.1. В скоупе

- Мобильный интерфейс клиента: расписание, детали слота, бронирование, мои брони, отмена, статус отмены скалодромом, выбор проката и оценка.
- Client API как контракт приложения: чтение расписания и деталей, создание и отмена брони, получение статуса, получение прокатных данных, приём оценки и связь с push-событиями.
- Клиентская обработка состояний загрузки, пустого состояния, ошибок сети, конфликта мест и отказа сервиса.
- Отображение адреса, тарифа и остатка прокатного фонда только в том виде, в котором их предоставляет API.

### 8.2. Вне скоупа

- Реализация и изменение бэкенда, его базы данных, транзакций, SLA и внутреннего маппинга.
- Создание, редактирование и публикация расписания.
- Админка владельца и любые административные функции.
- Мобильное приложение или интерфейс инструктора.
- Онлайн-оплата, платёжный шлюз, чеки, возвраты и финансовая отчётность.
- Миграция исторических данных и заполнение легаси-схемы.

### 8.3. Контрактные обязательства приложения

- Существующий бэкенд остаётся источником истины по свободным местам и статусам.
- Client API скрывает внутренние модели, но предоставляет согласованный клиентский контракт.
- Приложение не обещает сохранение брони при отсутствии подтверждения от API.
- Приложение не изменяет слоты, инструкторов, зоны и правила вместо внешней инфраструктуры.

|---|---|---|

| `Slot` | `id`, `session_id`, `starts_at`, `capacity`, `available_places`, `status` | Расписание и доступность |
| `Booking` | `id`, `slot_id`, `client_id`, `status`, `equipment`, `cancel_deadline`, `cancel_reason` | Запись одного клиента |
| `EquipmentOption` | `type`, `available_count`, `price` | Своё снаряжение или прокат |
| `Rating` | `booking_id`, `instructor_id`, `score`, `created_at` | Оценка завершённой тренировки |
| `Notification` | `type`, `title`, `body`, `created_at`, `read_at` | Уведомление об изменении записи |
