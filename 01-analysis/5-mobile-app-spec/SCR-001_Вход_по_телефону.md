# SCR-001 — Вход по номеру телефона

## 1. Метаданные

| Поле | Значение |
|---|---|
| ID | `SCR-001` |
| Название | Вход по номеру телефона |
| Роль | Клиент |
| Тип | Форма авторизации |
| Маршрут | `auth/phone` |
| Точка входа | Запуск приложения, истёкшая сессия, UC-001 |
| Связанные требования | `BR-001`, `BR-012`, `FR-001`, `NFR-004`, `US-001`, `UC-001` |
| Версия | 1.0.0 |
| Приоритет | Must |

## 2. Цель и пользовательский сценарий

- Цель: получить номер телефона Клиента в формате E.164 и запросить SMS-код для перехода к авторизации.
- Основной сценарий: Клиент открывает экран, вводит номер в маске, подтверждает отправку кода и попадает на `SCR-002`.
- Условия доступа: экран доступен без Bearer-токена; сессия отсутствует или истекла.
- Результат: валидный номер отправлен в `POST /auth/request-code`, приложение запоминает номер только как временный контекст следующего экрана.

## 4. Состояния экрана

| Состояние | Условие | Отображение | Действие клиента |
|---|---|---|---|
| Initial | Экран открыт, номер ещё не введён | Пустое поле, подсказка формата, disabled CTA | Ввести номер |
| Loading | Валидный номер отправлен, ожидается ответ | Spinner в CTA, поле read-only, повторное нажатие заблокировано | Дождаться ответа |
| Success | API вернул HTTP 202 | Краткое уведомление «Код отправлен» и переход на `SCR-002` | Ввести код |
| Empty | Поле пустое или пользователь очистил номер | Подсказка ввода без сообщения об API-ошибке | Ввести номер и повторить |
| Error | API вернул 400, 429 или 503 | Понятное сообщение, код ошибки не выводится как основной текст | Исправить номер либо повторить после устранения причины |
| Offline | Нет сети | «Нет подключения. Проверьте сеть и повторите запрос» | Включить сеть и повторить |
| Forbidden | Endpoint публичный и 403 не предусмотрен контрактом | Доступ к форме не блокируется; при неожиданном запрете показывается безопасное сообщение и возврат на экран входа | Повторить авторизацию |

## 5. Взаимодействие с API

| Вызов | Endpoint / метод | Назначение | Перед вызовом | Обработка ответа | Обработка ошибки |
|---|---|---|---|---|---|
| API-AUTH-001 | `POST /auth/request-code` | Отправить SMS-код | Валидный `phone`, нет активного повторного запроса | `202 RequestCodeResponse`: сохранить телефон для `SCR-002`, перейти | `400`: исправить формат; `429`: показать `retry_after`; `503`: retry с задержкой |

Требования к обработке:

- Перед отправкой проверить `^\+7[0-9]{10}$` после удаления маски.
- Не отправлять запрос при пустом, неполном или невалидном номере.
- Один активный запрос; повторное нажатие блокируется до терминального ответа.
- При 429 использовать `retry_after` из ответа и не обходить таймер.
- При 503 разрешить ручной Retry, не создавая локальный статус кода.

## 6. Валидация и правила

- Поле `phone` обязательно.
- Разрешённый формат — E.164 для рынка +7: `+7XXXXXXXXXX`.
- Ввод принимает только цифры; маска не меняет передаваемое нормализованное значение.
- Номер не сохраняется как разрешение до успешной проверки SMS.
- При 400 поле остаётся редактируемым и содержит конкретное сообщение.
- При 429 CTA блокируется до `retry_after`, но поле можно редактировать.
- При отсутствии сети запрос не создаётся локально в статусе «Отправлено».
- Экран не предоставляет вход Администратору или Инструктору.

## 7. Acceptance Criteria

### AC-SCR-001-001 — Валидный номер и успешная отправка

**Связанные требования:** FR-001, NFR-004, BR-001

**Given** экран открыт и номер ещё не введён,
**When** Клиент вводит валидный `+7XXXXXXXXXX` и нажимает «Получить код»,
**Then** приложение вызывает `POST /auth/request-code`, показывает Loading, а после HTTP 202 переходит на `SCR-002` с сохранённым номером.

### AC-SCR-001-002 — Невалидный номер

**Связанные требования:** FR-001, NFR-004

**Given** поле содержит неполный номер или символы,
**When** Клиент нажимает «Получить код»,
**Then** отображается ошибка формата, API не вызывается, а CTA остаётся недоступной до исправления.

### AC-SCR-001-003 — Ограничение API и отсутствие сети

**Связанные требования:** FR-001, NFR-004

**Given** номер валиден,
**When** API возвращает 429 или 503 либо приложение обнаруживает Offline,
**Then** Клиент видит соответствующее состояние, понимает ограничение и может повторить запрос без создания ложного подтверждения.
