# SCR-002 — Ввод и проверка SMS-кода

## 1. Метаданные

| Поле | Значение |
|---|---|
| ID | `SCR-002` |
| Название | Ввод и проверка SMS-кода |
| Роль | Клиент |
| Тип | Форма подтверждения |
| Маршрут | `auth/verify-code` |
| Точка входа | Успешный HTTP 202 на `SCR-001`, повторная авторизация |
| Связанные требования | `BR-001`, `BR-012`, `FR-001`, `NFR-004`, `US-001`, `UC-001` |
| Версия | 1.0.0 |
| Приоритет | Must |

## 2. Цель и пользовательский сценарий

- Цель: подтвердить номер телефона шестизначным SMS-кодом и получить Bearer-токен.
- Основной сценарий: Клиент вводит шесть цифр, отправляет код, после HTTP 200 сохраняет токен и открывает `SCR-003`.
- Условия доступа: номер прошёл форматную проверку и на `SCR-001` получен HTTP 202.
- Результат: создана авторизованная сессия, номер телефона подтверждён, клиент может просматривать расписание.

Обязательные элементы:

- Заголовок и контекст отправленного SMS.
- Шесть отдельных цифровых полей с одной логической ошибкой.
- Таймер и безопасная повторная отправка.
- Primary CTA, disabled до заполнения кода.
- Loading, Error 400/401, Offline и Forbidden-ветки без потери контекста.
- Переход в расписание только после успешного ответа API.

| Состояние | Условие | Отображение | Действие клиента |
|---|---|---|---|
| Initial | Экран открыт, код ещё не введён | Шесть пустых полей, фокус на первом, disabled CTA | Ввести цифры |
| Loading | Заполнены 6 цифр и отправлен verify-запрос | Spinner, поля read-only, CTA заблокирована | Дождаться результата |
| Success | API вернул HTTP 200 и Bearer-токен | Краткое подтверждение, сохранение сессии, переход `SCR-003` | Просмотреть расписание |
| Empty | Пользователь очистил поля или код ещё не пришёл | Подсказка ввода и активная кнопка повторной отправки по таймеру | Ввести код или дождаться SMS |

## 5. Взаимодействие с API

| Вызов | Endpoint / метод | Назначение | Перед вызовом | Обработка ответа | Обработка ошибки |
|---|---|---|---|---|---|
| API-AUTH-002 | `POST /auth/verify-code` | Проверить шестизначный код и выдать Bearer-токен | Нормализованный `phone`, 6 цифр, не истёкший таймер resend | `200 TokenResponse`: сохранить токен, перейти `SCR-003` | `400`: неверный формат/код; `401`: код недействителен; `429`: соблюдать cooldown; `503`: retry |

Требования к обработке:

- Проверять ровно 6 цифр перед отправкой; не отправлять частичный код.
- Не хранить код в логах и не показывать его в push-контексте.
- Один активный verify-запрос; повторное нажатие блокируется.
- При 400/401 очищать только при явном истечении кода или оставлять редактируемые поля по тексту ошибки.
- При 429 использовать cooldown и запретить обход кнопкой.
- При неоднозначном сетевом ответе не создавать локальный Bearer-токен.

## 6. Валидация и правила

- `phone` берётся из контекста `SCR-001` и повторно проверяется как `+7XXXXXXXXXX`.
- `code` — ровно 6 цифр; другие символы удаляются или блокируются.
- Повторная отправка доступна только после `retry_after` ответа `POST /auth/request-code`.
- При 400 ошибка показывается рядом с полями кода, а не в техническом виде.
- При 401 код считается недействительным; переход в расписание запрещён.
- При 429 и 503 код не считается неверным; доступен безопасный повтор после ограничения/сети.
- Токен хранится только после успешного ответа и используется как Bearer для защищённых экранов.

## 7. Acceptance Criteria

### AC-SCR-002-001 — Успешная верификация

**Связанные требования:** FR-001, NFR-004, BR-001

**Given** номер подтверждён запросом SMS и пользователь вводит шесть цифр,
**When** он подтверждает код,
**Then** приложение вызывает `POST /auth/verify-code`, а после HTTP 200 сохраняет Bearer-токен и открывает `SCR-003`.

### AC-SCR-002-002 — Неверный или истёкший код

**Связанные требования:** FR-001, NFR-004

**Given** введены шесть цифр,
**When** API возвращает HTTP 400 или 401,
**Then** сессия не создаётся, поля остаются редактируемыми, показывается конкретная ошибка, а пользователь может запросить новый код после таймера.

### AC-SCR-002-003 — Resend и Offline

**Связанные требования:** FR-001, NFR-004

**Given** код не введён или сетевой запрос недоступен,
**When** истекает cooldown либо пользователь нажимает «Отправить код ещё раз»,
**Then** приложение не обходит таймер, при отсутствии сети не показывает отправку и предлагает повторить после подключения.
