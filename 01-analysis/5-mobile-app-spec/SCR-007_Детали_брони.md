# SCR-007 — Детали брони

## 1. Метаданные

| Поле | Значение |
|---|---|
| ID | `SCR-007` |
| Название | Детали брони |
| Роль | Клиент |
| Тип | Детали персональной записи |
| Маршрут | `bookings/{id}` |
| Точка входа | Выбор из `SCR-006`, успешное бронирование из `SCR-005`, push deep link |
| Связанные требования | `BR-007`, `BR-008`, `BR-010`, `BR-013`, `FR-007`, `FR-008`, `FR-009`, `FR-011`, `NFR-003`, `NFR-005`, `NFR-006`, `US-005`, `US-006`, `US-007`, `UC-004`, `UC-005` |
| Версия | 1.0.0 |
| Приоритет | Must |

## 2. Цель и пользовательский сценарий

- Цель: показать полный статус и детали одной брони, безопасно отменить её до дедлайна или открыть актуальную информацию после push.
- Основной сценарий: Клиент открывает бронь из списка, видит данные и статус; при `confirmed` и достаточном времени подтверждает отмену; после ответа API видит новый статус.
- Условия доступа: действует Bearer-токен; `booking.id` принадлежит текущему Клиенту; для deep link доступна запись в `GET /bookings/my`.
- Результат: статус, причина и доступные действия соответствуют серверному состоянию; push открывает нужную карточку без потери авторизации.

## 4. Состояния экрана

| Состояние | Условие | Отображение | Действие клиента |
|---|---|---|---|
| Initial | Открыта карточка, данные ещё не получены | Заголовок и Skeleton деталей | Дождаться |
| Loading | Загрузка `GET /bookings/my` для `booking.id` или отправка отмены | Skeleton/spinner, CTA disabled | Дождаться |
| Success | API вернул актуальную запись | Полная карточка и действия по статусу | Отменить, оценить или вернуться |
| Empty | `booking.id` не найден в актуальном списке | «Бронь не найдена» и возврат в `SCR-006` | Вернуться к списку |
| Error | API вернул 400, 401, 404 или 503 | Сообщение с Retry; 400 — дедлайн; 401 — вход | Повторить или вернуться |
| Offline | Нет сети, есть локальные данные | Read-only данные с меткой неактуальности; отмена и оценка заблокированы | Обновиться после подключения |
| Forbidden | Нет сессии или `booking.id` принадлежит другому клиенту | Данные не раскрываются, pending deep link можно продолжить после входа | Войти и повторить |

## 5. Взаимодействие с API

| Вызов | Endpoint / метод | Назначение | Перед вызовом | Обработка ответа | Обработка ошибки |
|---|---|---|---|---|---|
| API-BOOKING-003 | `GET /bookings/my` | Найти и обновить детали записи, включая deep link | Bearer-токен; `booking.id` из маршрута или push | `200 MyBookingsResponse`: найти `id`, заполнить `SCR-007` | `401`: вход с pending link; `503`: Retry; не найдено — Empty |
| API-BOOKING-002 | `POST /bookings/{id}/cancel` | Отменить бронь клиентом | Статус `confirmed`; серверный `now <= cancel_deadline`; подтверждение UI | `200 Booking`: заменить карточку, показать `cancelled_by_client` | `400`: дедлайн/неверное состояние; `401`: вход; `404`: Empty; `503`: Retry |
| API-PUSH-001 | `POST /devices/push-token` | Зарегистрировать токен после разрешения пользователя | Bearer-токен; `platform`, `push_token`, `is_enabled` | `201 NotificationDevice`: сохранить статус регистрации | `400/401/409`: не блокировать чтение деталей, предложить повторить |

Требования к обработке:

- Дедлайн не вычислять только по часам устройства; использовать `starts_at` и серверное время источника истины.
- При `now > cancel_deadline` не отправлять cancel POST и показать ограничение.
- При 200 заменить данные ответа, а не только менять label локально.
- При push сначала обновить `GET /bookings/my`, затем выбрать `booking.id`; не открывать stale detail без маркировки.
- При 401 сохранить только безопасный pending route `booking_id`, затем продолжить после входа.
- Не отправлять push-token без явного разрешения и не использовать его для авторизации.

## 6. Валидация и правила

- `id` — UUID, принадлежащий текущему Bearer-клиенту.
- Для `confirmed` дедлайн равен `slot.starts_at - 2 hours`; разрешена отмена при `now <= deadline`.
- Для `cancelled_by_client` и `cancelled_by_venue` кнопка отмены скрыта.
- Для `cancelled_by_venue` отображаются точные status label «Отменена скалодромом» и непустая причина.
- Для `completed` без rating доступна оценка; для `rated` — просмотр.
- Booking не редактируется мобильным приложением.
- Booking не удаляется при отмене скалодромом.
- Повторная запись в отменённый слот недоступна.
- Для отправки отмены обязателен Bearer-токен.

## 7. Acceptance Criteria

### AC-SCR-007-001 — Детали и отмена до дедлайна

**Связанные требования:** FR-007, FR-008, BR-007, NFR-003

**Given** бронь имеет статус `confirmed` и до `starts_at` осталось не менее 2 часов,
**When** Клиент подтверждает отмену,
**Then** приложение вызывает `POST /bookings/{id}/cancel` и после HTTP 200 показывает статус «Отменена клиентом» и обновляет детали.

### AC-SCR-007-002 — Отмена после дедлайна

**Связанные требования:** FR-008, BR-007, NFR-003

**Given** до начала тренировки осталось менее 2 часов,
**When** Клиент открывает детали,
**Then** кнопка отмены заблокирована, объяснено окно 2 часа, а API-запрос отмены не отправляется.

### AC-SCR-007-003 — Отмена скалодромом

**Связанные требования:** FR-009, FR-011, BR-008, BR-010

**Given** приходит push с `booking_id` или пользователь открывает запись,
**When** актуальный API возвращает `cancelled_by_venue` и reason,
**Then** экран показывает «Отменена скалодромом», причину, сохраняет бронь и блокирует повторную запись в слот.

### AC-SCR-007-004 — Deep link и истёкшая сессия

**Связанные требования:** FR-011, FR-009, NFR-005, NFR-003

**Given** push содержит корректный `booking_id`,
**When** пользователь открывает уведомление без действующей сессии,
**Then** приложение сохраняет безопасный pending deep link, после входа обновляет `GET /bookings/my` и открывает только найденную бронь.
